# Redis 核心知识与面试主线

本文既是一份 Redis 面试知识地图，也对应本项目中的购物车和商品缓存实现。学习时不要只背结论，应同时在 `redis-cli` 和代码中验证。

## 1. Redis 是什么，为什么快

Redis 是以内存为主要存储介质的数据结构服务器，支持 TTL、持久化、复制和集群。它常用于缓存、购物车、计数器、排行榜、限流和分布式协调。

Redis 快的主要原因：

- 数据主要在内存中，避免大量磁盘随机 IO。
- 核心命令执行路径短，数据结构经过优化。
- 使用 IO 多路复用处理大量连接。
- 命令执行通常串行，减少锁和线程切换开销。

“Redis 是单线程”并不严谨：核心命令执行长期采用单线程模型，但网络 IO、持久化和异步删除等工作可以使用其他线程。串行执行也意味着慢命令和大 Key 操作可能阻塞其他请求。

## 2. 常用数据结构

### String

```redis
SET product:detail:1 '{"id":1}' EX 600
GET product:detail:1
INCR page:view:1
```

适合 JSON 缓存、计数器、验证码、Session 和简单锁。

### Hash

```redis
HSET cart:1 1001 2
HSET cart:1 1002 1
HGETALL cart:1
```

适合购物车和对象字段。本项目的结构是：

```text
key=cart:{userId}, field=skuId, value=quantity
```

### List

有序、可重复，支持两端操作，适合简单队列和最新列表。可靠消息通常优先考虑 Redis Stream、RabbitMQ 或 Kafka。

### Set

无序、不重复，适合收藏、标签、去重、共同关注和集合运算。

### Sorted Set

成员带 score 并按分数排序，适合排行榜、热度榜、时间排序和简单延迟任务。

### Bitmap、HyperLogLog、Stream

- Bitmap：签到、活跃状态等布尔型统计。
- HyperLogLog：低内存近似去重计数，例如 UV，结果存在误差。
- Stream：带消息 ID、消费者组、确认和 Pending 列表的消息流。

## 3. TTL、过期删除与内存淘汰

```redis
EXPIRE cart:1 2592000
TTL cart:1
```

Redis 结合惰性删除和定期删除处理过期 Key：访问时发现过期就删除，同时周期性抽样清理。TTL 表示过期后不应再返回数据，不代表那个毫秒一定完成物理内存释放。

达到 `maxmemory` 后常见淘汰策略包括：

- `noeviction`：拒绝新的写操作。
- `allkeys-lru`：从所有 Key 中近似淘汰最近最少使用的数据。
- `allkeys-lfu`：近似淘汰访问频率最低的数据。
- `volatile-lru/lfu`：只处理设置 TTL 的 Key。
- `volatile-ttl`：优先淘汰剩余 TTL 更短的 Key。

购物车比普通商品缓存更重要，两类数据混在同一实例并使用 `allkeys-lru`，可能导致购物车被当作普通缓存淘汰。生产中应考虑实例隔离、持久化或数据库兜底。

## 4. RDB 与 AOF

- RDB：周期性生成全量快照，文件紧凑、恢复较快，但快照间数据可能丢失。
- AOF：记录写命令，数据丢失窗口更小，但文件和恢复成本通常更高，需要重写。

AOF 常见刷盘策略是 `always`、`everysec` 和 `no`。两种持久化可以同时启用，但 Redis 持久化不能替代异地备份，也不能自动提供关系数据库级别的可靠性。

## 5. 缓存穿透、击穿和雪崩

| 问题 | 本质 | 常见措施 |
|---|---|---|
| 穿透 | 请求的数据根本不存在 | 空值缓存、布隆过滤器、校验与限流 |
| 击穿 | 单个热点 Key 过期，大量请求回源 | 互斥重建、逻辑过期、提前刷新 |
| 雪崩 | 大量 Key 同时过期或 Redis 故障 | TTL 随机化、高可用、限流、熔断和降级 |

空值缓存 TTL 应短于正常数据，否则刚创建的数据可能长时间仍显示不存在。布隆过滤器可能误判“存在”，但不会把实际存在的数据判定为不存在。

热点互斥重建通常要双重检查：缓存未命中后获取锁，再查一次缓存，然后才查询数据库。逻辑过期允许返回旧值并异步刷新，适合能容忍短时间旧数据的场景。

## 6. 热 Key 与大 Key

热 Key 是访问集中，例如爆款商品 `product:detail:1`；大 Key 是单个 value 很大或集合成员过多。

热 Key 风险：单节点 CPU、带宽或连接压力集中，增加其他分片也无法自动分摊。常见措施包括本地缓存、热点副本、限流、预热和业务隔离。

大 Key 风险：网络传输慢、阻塞命令、复制和迁移压力大、集群内存不均。应限制大小、拆分数据、分页读取，使用 `SCAN/HSCAN` 代替危险的全量遍历，删除大 Key 时考虑 `UNLINK`。

普通购物车按用户拆 Key，天然较分散，但仍应限制购物车 SKU 种类。商品详情更容易成为热 Key。

## 7. 原子性、Pipeline、事务和 Lua

单条 Redis 命令通常是原子的，但 `GET → 计算 → SET` 不是一个原子操作。

- Pipeline：批量发送命令以减少网络往返，不保证原子性。
- `MULTI/EXEC`：命令连续执行，但不提供关系数据库式完整回滚。
- `WATCH`：监视 Key，发生变化时让事务失败，类似乐观锁。
- Lua：包含判断和计算，并作为一个整体执行。

本项目购物车加入商品使用 Lua，原子完成读取、累加、99 件上限检查和 TTL 刷新。Lua 脚本也不能过慢，否则会阻塞其他命令。

## 8. 分布式锁

基本加锁形式：

```redis
SET lock:order:1 unique-request-id NX PX 30000
```

释放时必须比较 value 后再删除，通常用 Lua，防止误删已经属于其他请求的新锁。还必须考虑锁超时、续期、客户端宕机、网络分区、可重入、主从切换和 fencing token。

能够用数据库唯一约束或乐观锁解决的问题，不应机械地增加 Redis 分布式锁。Redisson 可以减少样板代码，但不能替代理解一致性边界。

## 9. Cache Aside 与一致性

查询流程：

```text
读取缓存 → 命中则返回
        → 未命中则查数据库、写缓存、返回
```

更新流程通常是：

```text
更新数据库 → 删除缓存
```

一般删除而不是直接更新缓存，因为缓存模型可能复杂、并发更新容易覆盖，而且冷数据没必要立即重建。通常先更新数据库再删除缓存，降低旧值被并发回填后长期保留的概率。

数据库成功但删除缓存失败仍可能不一致，可通过短 TTL、重试、MQ、Outbox 或订阅数据库变更日志改善。缓存多数追求最终一致性，而不是强一致性。

本项目在数据库事务提交后的 `afterCommit` 中删除商品缓存，避免数据库回滚但缓存已经被删。商品缓存故障时降级查询数据库；购物车故障时返回 503，因为前者是副本，后者是用户状态源。

## 10. 主从、Sentinel 与 Cluster

- 主从复制：主节点写，从节点异步复制并可承担读取；可能丢失尚未复制的数据。
- Sentinel：监控节点、自动故障转移和通知客户端，不负责数据分片。
- Cluster：使用 16384 个槽进行数据分片，并支持多主和故障转移。

槽计算可以简化理解为：

```text
key → CRC16(key) % 16384 → slot → node
```

Hash Tag 让相关 Key 落在同一槽，例如 `cart:{1001}` 和 `cart-meta:{1001}`。跨槽多 Key 命令和 Lua 会受限制，因此 Key 设计会影响未来集群化。

## 11. 本项目对应关系

```text
Redis Hash       → 用户购物车
TTL              → 购物车 30 天过期、商品详情约 10 分钟
Lua              → 购物车原子累加、结算后条件删除
Cache Aside      → 商品详情缓存
空值缓存         → 防止不存在商品反复穿透数据库
TTL 随机抖动     → 减少大量商品同时过期造成雪崩
失败开放         → 商品缓存异常时回源 PostgreSQL
afterCommit      → 数据库提交成功后再清理缓存或购物车
```

## 12. 面试速记

1. Redis 主要在内存中工作，结合高效结构、IO 多路复用和较少锁竞争获得高性能。
2. String、Hash、List、Set、ZSet 是最常用结构。
3. 过期 Key 通过惰性删除和定期删除结合处理。
4. 内存不足时由淘汰策略决定删除 Key 还是拒绝写入。
5. RDB 是快照，AOF 是写日志。
6. 穿透是不存在，击穿是单热点失效，雪崩是大量失效或整体故障。
7. 热 Key 是访问集中，大 Key 是数据或成员过多。
8. Pipeline 减少网络往返，Lua 解决组合逻辑原子性。
9. Cache Aside 是读时回填、写时更新数据库后删缓存。
10. Sentinel 解决高可用，Cluster 解决分片和水平扩展。

## 13. 建议练习

```redis
HSET cart:1 1001 2
HINCRBY cart:1 1001 1
HGETALL cart:1
EXPIRE cart:1 300
TTL cart:1
GET product:detail:1
```

然后依次完成：观察缓存命中、删除缓存后观察 SQL 回源、请求不存在 ID 验证空值、修改商品验证缓存失效、让 Redis 停止并验证商品回源和购物车 503。最后再学习热点互斥重建、监控和 Redis Cluster。
